# Project Changelog - Odoo Clients 360 (ts_partner_app)
#
# Internal development history, kept for reference only — not shipped as the
# module's public-facing changelog. The module's version was reset to 19.0.1 for
# its first public/free release; see CHANGELOG.txt for the release-facing log
# going forward. Entries below use the pre-reset internal version numbers
# (19.0.01 through 19.16.7) exactly as they were made; never edited retroactively.

## [19.16.7] - 2026-08-20
### Changed
- Replaced the old FontAwesome-based `static/description/index.html` (the Apps-list
  description page) with the full store-page design: hero, 9-pillar feature grid,
  screenshot gallery (linking to the 4 real screenshots under `static/screenshots/`

## [19.16.6] - 2026-08-20
### Changed
- Switched from a paid OPL-1 license to LGPL-3 and made the module free — removed
  the `price`/`currency` keys from the manifest entirely.

## [19.16.5] - 2026-08-20
### Changed
- Made the state/stage sync from 19.16.4 symmetric: setting `state` alone (without
  `stage_id`) now also moves the stage to match, not just the other way around. Every
  existing write path already sets both together deliberately, so this is pure
  defense-in-depth for anywhere else that might set just one in the future.
- Checked every other model in the module for the same dual state/stage_id pattern —
  `partner.asset` is the only one that has it; nothing else needed this fix.

## [19.16.4] - 2026-08-20
### Fixed
- Header button visibility (and everything else keyed off `state`) didn't update when
  changing an asset's stage via the clickable statusbar or Kanban drag — those only
  write `stage_id`, and nothing kept `state` in sync with it. Only the cron/health-check
  paths set both together, so a manual stage change silently drifted the two apart.
  `write()` now syncs `state` to match whenever `stage_id` changes to one of the 4
  built-in stages and `state` isn't also being set explicitly in the same call. Also
  fixed the one asset this had already happened to live.

## [19.16.3] - 2026-08-20
### Changed

  hidden on New (visible on Running, To Renew, Closed), **New Client Project** now

## [19.16.2] - 2026-08-20
### Changed

  actually makes sense for the asset's current status shows up: **Create Sale Offer**

## [19.15.3] - 2026-08-20
### Fixed
- Remove Imported Products, tested live: a product already used on a sale order/invoice
  line surfaced a raw database foreign-key error, not a clean Odoo message — turns out
  `product.product` doesn't guard against this deletion case itself. Worse, since
  `unlink()` on a recordset is all-or-nothing, one blocked product stopped every other
  product from being removed too. Now removes each product individually (isolated in
  its own savepoint), so it removes everything it safely can and reports which specific
  ones are still in use, by name, in a clear notification instead of a raw error.

## [19.9.10] - 2026-08-19
### Fixed
- Root-caused and fixed why re-running "Import Demo Data" kept reintroducing the
  "Trial"/"VIP Client" untranslated-tag drift from 19.9.9: `_ensure_record`'s
  `create()`/`write()` calls ran under whatever language the current session had
  (this DB defaults to Bosnian), so writing a hardcoded English literal into a
  translatable field's `write()` landed in the **bs_BA** slot, silently clobbering
  the real translation with the English text every single re-import. `_ensure_record`
  now forces `lang='en_US'` for all its create/write calls, so demo data always writes
  to the English slot and never touches an existing Bosnian translation again.

## [19.9.7] - 2026-08-19
### Fixed
- 21 Bosnian translations existed but silently didn't apply everywhere they should,
  because Odoo's `.po` loader matches by the `#:` occurrence comment, not just the msgid
  text — reusing an already-translated string in a new spot (a new field, a new action,
  a catalog entry) doesn't automatically translate that new spot unless its occurrence
  is listed too. Concretely broken: the **New Client Project** action/dialog title (still
  showed the English string), the Client Stages/Tags action names and view titles
  (already patched live in 19.9.1, but would have reverted to English on any fresh
  install since the `.po` itself was never fixed), the CRM/Sales/Purchase/Helpdesk/
  Manufacturing catalog task names, the "Tasks" wizard-step label, and generic field
  labels (Name, Sequence, Created by/on, Last Updated by/on, Display Name, ID) on the
  three newer template/wizard models. Synced every entry's occurrences to the current
  codebase so all of these now translate correctly.

## [19.9.6] - 2026-08-19
### Fixed
- Expiry cron and renewal-confirmation logic (`_cron_send_expiry_notifications` in
  `partner_asset.py`, `action_confirm` in `sale_order.py`) looked up the "To Renew" /
  "Running" Kanban stage by a hardcoded English `name` search. Since `name` is
  translatable and this DB's active language is Bosnian, the search silently matched
  nothing once those stage names were actually translated — `state` updated correctly
  but `stage_id` (and therefore the Kanban card) quietly fell out of sync. Both now use
  `env.ref()` against the stage's xmlid instead, matching the pattern already used
  correctly in `action_check_health`.
- `partner.asset.tag`'s name-uniqueness constraint still used the deprecated
  `_sql_constraints` list, which Odoo 19 ignores entirely (logs a warning, creates no
  DB constraint) — duplicate tag names could be created. Converted to `models.Constraint`,
  matching every other model in the module.
### Added
- Bosnian translations for the entire New Client Project wizard and Project Task
  Templates catalog (99 strings) — the module's most recently built feature had zero
  translation coverage until now: wizard labels/buttons/help text/error messages, the
  config screen, and all 49 seeded catalog task names.

## [19.8.7] - 2026-08-19
### Fixed
- New Client Project wizard: fixed a recurring "Missing required value for the field
  'Name'" error that survived the previous fixes because it wasn't actually about any
  single missing view field — it was that the wizard opened as an unsaved/virtual record
  (via `default_get`), and the browser's local cache for that kind of record has proven
  unreliable across repeated save round-trips for multi-field One2many data. The wizard
  record (and its 49 template lines) is now created **server-side**, fully persisted,
  the moment you click "New Client Project" — the dialog always opens on a real,
  already-saved record, so every subsequent click (toggling a task, Recalculate PM,
  switching steps, Create Project) is an ordinary update to existing rows, not a
  from-scratch creation the browser has to get exactly right.

## [19.8.6] - 2026-08-19
### Fixed
- New Client Project wizard: the "Modules" step wasn't clickable on the statusbar.
  `clickable="1"` needs to be inside the widget's `options` dict
  (`options="{'clickable': '1'}"`), not a bare XML attribute — the bare attribute is
  silently ignored, matching how core Odoo (project.task's own status bars) does it.

## [19.8.5] - 2026-08-19
### Fixed
- New Client Project wizard: eliminated the "Missing required value" errors for good by
  removing their root cause instead of chasing individual fields. The **Next: Modules** /
  **Back: Tasks** buttons each forced a full save-and-reopen round trip (any `type="object"`
  button does), and each of those trips was a fresh chance for the browser's local record
  to drop a field the view didn't retain. Replaced them with a clickable **statusbar**
  (Tasks / Modules) at the top of the wizard — switching steps is now a pure client-side
  field change with no server round trip at all. The wizard is now only ever actually
  saved once, when **Create Project** is clicked. The Recalculate PM button also no longer
  forces a dialog reopen; it now just updates the line in place.
